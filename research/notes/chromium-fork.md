# Chromium fork with a native Swift/AppKit browser UI — feasibility research

Date: 2026-10-01. Scope: a 1–2 person team building a macOS-only browser whose chrome (window, sidebar, address bar, tab strip) is reimplemented in Swift/AppKit instead of Chromium's Views UI. Sources are cited inline; where I could not find a primary source I say so.

---

## 1. Summary & verdict

- **A Chromium fork is sustainable for a 1–2 person team only if the patch surface is small and the build is automated.** The forks that survive at that team size (ungoogled-chromium: 109 patches; Helium: 343 patches + ungoogled's; Thorium: 3 people, "8+ hours of focused, non-stop work" per rebase, now tracking LTS only) all keep Chromium's Views UI and change behaviour, not the UI architecture. No open-source fork today replaces `BrowserView` with a native AppKit window.
- **Replacing the browser chrome natively is technically possible but is the single largest, most rebase-hostile change you can make to `//chrome`.** `BrowserWindow` (`chrome/browser/ui/browser_window.h`) is still an abstract interface (74 pure virtuals + ~24 from `ui::BaseWindow`), but the header itself states "In production code BrowserView is the only subclass for BrowserWindow", and the factory (`chrome/browser/ui/views/frame/browser_window_factory.cc`) hard-codes `new BrowserView(browser)`. Dozens of feature surfaces (permission prompts, autofill popups, password bubbles, download bubble, infobars, extensions menu, find bar, translate/bookmark bubbles, tab search, app menu) are implemented only in `chrome/browser/ui/views/` and reached through factory functions or `BrowserWindow` methods that return Views types.
- **Hosting Chromium web content in an arbitrary AppKit hierarchy is the easy part and is well-supported:** `WebContents::GetNativeView()` returns the `WebContentsViewCocoa` NSView; the renderer paints into a CALayer tree the browser attaches to that view. Opera did exactly this in 2013 ("we stripped away Chromium's UI layer, and built it piece by piece from scratch"), Arc/Dia do it today (closed source, Swift), Phi Browser does it today (AppKit/SwiftUI client over a proprietary Chromium framework).
- **Realistic plan for a tiny team:** do NOT re-implement every `BrowserWindow` surface natively. Implement the window frame, tab strip, sidebar, and omnibox natively, and keep Chromium's Views machinery alive for secondary UI (bubbles, dialogs, permission prompts, autofill popups) by anchoring Views bubbles to screen rects (`BubbleDialogDelegateView::SetAnchorRect` + `set_parent_window`). Even that is a multi-month effort and an ongoing tax at every Chromium milestone — which since Chrome 153 (8 Sept 2026) ships **every two weeks**, with weekly security refreshes.
- **Build cost on an M1 Max (10-core, 64 GB):** expect roughly 1.5–2.5 h for a clean non-official release build (`is_debug=false`, `symbol_level=0`, no LTO/PGO) based on reported M1 Pro (1:17) and M2 Max (1:30) numbers; an `is_official_build=true` + ThinLTO + PGO build like ungoogled-chromium's takes several hours (their CI on an 8-CPU/24 GB Depot M2/M4 runner needs ~6.5 h of compile wall time for arm64). Google's remote build (RBE) is not available to you. Disk: budget 100+ GB.
- **Verdict:** feasible as a *product bet* only if (a) one person is willing to be a full-time Chromium integrator for the first 6–9 months, (b) you adopt Brave-style `chromium_src` overrides for the UI swap and keep raw patches minimal, (c) you accept living 1–2 milestones behind stable or on Extended Stable (8-week cadence), and (d) you do not need Chrome Sync, bundled Widevine, or Google Safe Browsing (commercial use of the SB API is prohibited; Web Risk is the paid path). A CEF-based route is 3–5x cheaper to reach "works" but caps you at Alloy-style embedding (no Chrome extension UI, no `chrome://` pages, fewer Chrome features) when you want your own native chrome. Details in §9.

### 2.2 Incremental builds

No Apple-Silicon-specific primary numbers found. What the docs say:
- `is_component_build = true` "creates many small dylibs instead of a single large executable. This makes incremental builds much faster, at the cost of producing a binary that opens less quickly." `symbol_level = 0` makes "both full rebuilds and linking faster". `is_debug = false` → "linking is a lot faster". `use_lld = false` (Apple's `ld`) "improves link speed" for local arm64 builds. ([docs/mac_build_instructions.md](https://chromium.googlesource.com/chromium/src/+/main/docs/mac_build_instructions.md))
- `blink_symbol_level=0` and `v8_symbol_level=0` disable symbols for those components; `symbol_level=1` gives stack traces without line info ([docs/linux/build_instructions.md](https://chromium.googlesource.com/chromium/src/+/main/docs/linux/build_instructions.md)).
- Signing requires a static build: "Signing requires a statically linked build (i.e. `is_component_build = false`)" ([chrome/installer/mac/signing/README.md](https://github.com/chromium/chromium/blob/main/chrome/installer/mac/signing/README.md)). So you need two out-dirs: a component dev build for iteration and a static release build for shipping.
- Judgment (not sourced): in a component build, editing one `.mm` in your UI target and relinking a small dylib is seconds to a minute; touching a widely-included header in `//base` or `//content/public` is a 20–60 minute rebuild on 10 cores.

### 2.4 Checkout size and `gclient sync`

- `fetch chromium` "may take 30 minutes on even a fast connection, and many hours on slower ones"; the git cache "mirrors every repo it fetches (~30 GB for Chromium)". ([mac_build_instructions.md](https://chromium.googlesource.com/chromium/src/+/main/docs/mac_build_instructions.md))
- Linux docs: "At least 100GB of free disk space"; "~50-80GB on HDD for build"; "more than 16GB [RAM] is highly recommended". ([linux build_instructions.md](https://chromium.googlesource.com/chromium/src/+/main/docs/linux/build_instructions.md))
- Your 1.2 TB is ample for two out-dirs plus a git checkout.
- **ungoogled-chromium and Helium avoid depot_tools/gclient entirely**: they download the official source tarball `chromium-<version>-lite.tar.xz` from `commondatastorage.googleapis.com/chromium-browser-official/` and fetch the few binary deps they need separately ([ungoogled-chromium downloads.ini](https://github.com/ungoogled-software/ungoogled-chromium/blob/master/downloads.ini)). This sidesteps gclient hooks and DEPS churn but means no git history for bisecting upstream, and every version bump is a fresh ~5 GB tarball + clean build. Brave uses depot_tools (`pnpm run sync` → gclient) ([brave-core README](https://github.com/brave/brave-core)).
- When is `gclient sync` painful? Every milestone bump re-syncs ~hundreds of DEPS (clang, rust toolchain, Skia, V8, ANGLE…) and runs hooks; a stale checkout crossing a toolchain roll often requires `gclient sync -D` and a clean out-dir. Switching between release branches needs `--with_branch_heads --with_tags` ([docs/working_with_release_branches.md](https://chromium.googlesource.com/chromium/src/+/main/docs/working_with_release_branches.md)). Judgment: with a 2-week milestone cadence you will do this twice a month.

Chromium's own cadence, which sets the clock for all of the above: "Chrome ships a new milestone (major version) to the stable channel every two weeks" (since Chrome 153, 8 Sept 2026); "Weekly updates (called refreshes) are shipped to stable to deploy security fixes"; Extended Stable: "every fourth milestone branch for six additional weeks … a new milestone is shipped every eight weeks" ([docs/process/release_cycle.md](https://chromium.googlesource.com/chromium/src/+/main/docs/process/release_cycle.md), [Chrome blog, 8 Sept 2026](https://developer.chrome.com/blog/chrome-two-week-start)).

**Pros/cons for a fork whose main change is replacing the browser UI:**

- **quilt-style patch series (ungoogled/Helium):** simplest tooling, pristine tree, easy to audit. Bad fit for a UI replacement: you'd carry one giant patch that deletes/replaces `BrowserView` wiring and that will conflict every milestone (Google refactors `chrome/browser/ui/views/frame/` constantly — e.g. `BrowserFrame`→`BrowserWidget`, `BrowserFrameMac`→`BrowserNativeWidgetMac` renames visible in the tree today). Fine for everything *else* (branding, services, flags).
- **Brave-style `chromium_src` overrides + minimal patches:** best fit. Your native window lives in your own directory (`//room/...`) as ordinary GN targets; a handful of small patches redirect `BrowserWindow::CreateBrowserWindow` and the few `chrome/browser/ui/*` factory functions to your implementations; `chromium_src` shadow headers let you virtualize or rename what you need without diffing upstream files. Costs: a custom include-path setup and the discipline to keep patches "trivial changes, not nested logic changes".
- **Vivaldi-style GN extensions + submodule:** similar to Brave's; adds the ability to inject sources into upstream targets without editing BUILD.gn. More infrastructure than a 2-person team wants to own.
- **Thorium-style copied files:** easiest to start, worst to rebase ("don't copy entire files … stale code during rebases", as Brave's doc warns, citing Electron's mistakes).

Time per rebase for a small team: ungoogled-level patch sets rebase in hours; Thorium's (more invasive, 3 people) take 8+ h of one person's focus per major; Vivaldi (900 files, ~20 devs) takes ~2 weeks per major. A native-UI fork sits between Thorium and Vivaldi in invasiveness. **Judgment:** plan on 1–3 days per milestone once stable, i.e. 15–30% of one engineer at a 2-week cadence, or follow Extended Stable (8 weeks) and backport security refreshes weekly (those are usually trivial).

## 4. The UI boundary (what must be implemented; difficulty)

### 4.1 Layering

- `//content` is "the core code needed to render a page using a multi-process sandboxed browser"; it "does not include Chrome features, e.g. extensions/autofill/spelling etc." Features like "Extensions, SpellCheck, Autofill, Sync, Safe Browsing, and Translate" are "implemented in `chrome`, while `content` only provides generic extension points" via `ContentBrowserClient`. `content_shell` is the minimal embedder. `content` cannot depend on `chrome`. ([content/README.md](https://github.com/chromium/chromium/blob/main/content/README.md))
- `toolkit_views = is_mac || is_win || is_linux || is_chromeos || is_fuchsia` — Views is unconditionally on for macOS ([build/config/ui.gni](https://github.com/chromium/chromium/blob/main/build/config/ui.gni)). You cannot build `//chrome` without Views; you can only avoid *using* `BrowserView` for the main window.

### 4.2 `BrowserWindow` and its macOS implementation today

- `chrome/browser/ui/browser_window.h` (525 lines, **74 pure-virtual methods**; inherits `ui::BaseWindow` which adds ~24 more: `Show/Hide/Close/Activate/SetBounds/GetNativeWindow/IsFullscreen/Maximize/…`). Groups: workspace/visibility; top-controls (mobile-style); toolbar/location bar (`UpdateToolbar`, `GetLocationBar`, `SetFocusToLocationBar`, `UpdateToolbarSecurityState`, `GetPinnedToolbarActions`); tab management (`OnActiveTabChanged`, `OnTabDetached`, `TabDraggingStatusChanged`, `CreateTabSearchBubble`); contents sizing; dialogs/bubbles (`GetStatusBubbles`, `GetAutofillBubbleHandler`, `ShowBookmarkBubble`, `ShowTranslateBubble`, `GetDownloadBubbleUIController`, `ShowAppMenu`, `ShowAvatarBubbleFromAvatarButton`, `ShowHatsDialog`, `ShowIntentPickerBubble`, `ConfirmBrowserCloseWithPendingDownloads`); theme (`GetNativeTheme/GetThemeProvider/GetColorProvider`); input (`PreHandleKeyboardEvent/HandleKeyboardEvent`, drag hooks); `CreateFindBar`, `GetWebContentsModalDialogHost`, `OpenEyeDropper`, `GetExclusiveAccessContext`, `GetAcceleratorProvider`. Header comment: "In production code BrowserView is the only subclass for BrowserWindow" and `virtual BrowserView* AsBrowserView() = 0;` ([browser_window.h](https://github.com/chromium/chromium/blob/main/chrome/browser/ui/browser_window.h)).
- Factory: `BrowserWindow::CreateBrowserWindow` in `chrome/browser/ui/views/frame/browser_window_factory.cc` does `view = new BrowserView(browser); auto browser_widget = std::make_unique<BrowserWidget>(view);` (ChromeOS gets `BrowserViewAsh`; mac adds `CreateMacOverlayView()` for immersive fullscreen). This is the one function a fork must redirect.
- `BrowserView` is 1,419 h + 6,182 cc lines. It is the `TabStripModelObserver`, the `views::ClientView`, the `ExclusiveAccessContext`, the `web_modal::WebContentsModalDialogHost`, hosts `ToolbarView`/`LocationBarView`/`TabStrip`/`InfoBarContainerView`/`SidePanel`/`ContentsWebView`, and is what every `ShowXxxBubble` anchors to.
- macOS specifics live in `chrome/browser/ui/views/frame/browser_native_widget_mac.{h,mm}` ("a NativeWidgetMac subclass that provides the window frame for the Chrome browser window": titlebar height, fullscreen transitions, touch bar, key equivalents, `GetWidgetParams`, `UseCustomFrame`), `browser_frame_view_mac.mm`, `immersive_mode_controller_mac.mm`, plus `chrome/browser/ui/cocoa/` (72 entries today vs 312 at M66): applescript, apps, bookmarks (menu bridge), fullscreen, profiles, renderer_context_menu, status_icons, tab_contents, touchbar, `main_menu_builder.mm`, `history_menu_bridge`, `tab_menu_bridge`, `browser_window_command_handler`, `chrome_command_dispatcher_delegate`, `javascript_app_modal_dialog_cocoa` (native NSAlert via `remote_cocoa::mojom::AlertBridge`), `simple_message_box_cocoa`, `confirm_quit_panel_controller`, `dock_icon`, `handoff_observer`, `share_menu_controller`, `window_size_autosaver`. These are reusable from a native window as-is.
- A newer, UI-agnostic layer is emerging: `chrome/browser/ui/browser_window/public/` (`browser_window_interface.h`, `browser_window_features.h`, `desktop_browser_window_capabilities.h`, `create_browser_window.h` with `BrowserWindowCreateParams`, 2025). `BrowserWindowInterface` exists "to prevent circular dependencies" and exposes `GetTabStripModel()`, `GetActiveTabInterface()`, `GetFeatures()`, `GetUnownedUserDataHost()`, etc. This refactor is in your favour: feature code increasingly talks to `BrowserWindowInterface`/`TabInterface` rather than `BrowserView`.

### 4.3 Web content hosting from AppKit — the easy part

- `WebContents::GetNativeView()` "Returns the native widget that contains the contents of the tab"; `GetContentNativeView()` the render view; `GetTopLevelNativeWindow()` "the outermost native view. This will be used as the parent for dialog boxes" ([content/public/browser/web_contents.h](https://github.com/chromium/chromium/blob/main/content/public/browser/web_contents.h)).
- On mac, `WebContentsViewMac` creates a `WebContentsViewCocoa` NSView through `remote_cocoa::WebContentsNSViewBridge`; `GetNativeView()` returns it; the `RenderWidgetHostViewCocoa` is added with `[GetInProcessNSView() addSubview:view_view positioned:NSWindowBelow relativeTo:nil]`; the code only assumes an NSWindow exists ("There is no NSWindow when running headless") and walks up to the root view, so the parent hierarchy is arbitrary ([web_contents_view_mac.mm](https://github.com/chromium/chromium/blob/main/content/browser/web_contents/web_contents_view_mac.mm)).
- `RenderWidgetHostViewMac` is "responsible for displaying the content of the web page, and integrating with the Cocoa view system"; output flows `ui::Compositor` → `BrowserCompositorMac` → `AcceleratedWidgetCALayerParamsUpdated(gfx::CALayerParams)` → the NSView's CALayer tree; the NSView can be in-process (`in_process_ns_view_bridge_`) or in an app-shim process over mojo (`remote_cocoa::mojom::RenderWidgetHostNSViewHost`) ([render_widget_host_view_mac.h](https://github.com/chromium/chromium/blob/main/content/browser/renderer_host/render_widget_host_view_mac.h), [components/remote_cocoa/README.md](https://github.com/chromium/chromium/blob/main/components/remote_cocoa/README.md)). The remote path is for PWA app shims; a normal browser window uses the in-process NSView, which you can `addSubview:` anywhere.
- Precedent: Opera's 2015 upstream patch "[Mac] Allow vibrancy & transparency on WebContentsView" exists precisely because Opera hosted `WebContentsViewCocoa` "inside NSVisualEffectView" in its native Mac UI ([chromium-reviews, Jan 22 2015](https://groups.google.com/a/chromium.org/g/chromium-reviews/c/pPV6hxDxYJo/m/RaHAlflShaMJ)).
- Caveats (judgment): focus/first-responder plumbing, `NSWindow`-level drag-and-drop, IME, accessibility (`content` AX tree is bridged from the browser process to the NSView — works in-process), and fullscreen/immersive behaviour all expect the `NativeWidgetMacNSWindow` conventions; you will reimplement some of what `BrowserNativeWidgetMac` and `ui/views/cocoa` do (command dispatch via `ChromeCommandDispatcherDelegate`, `BrowserWindowCommandHandler`, touch bar).

The pragmatic hybrid — native shell + Views secondary UI anchored by rect — removes most of the third category from the critical path.

### 4.5 Could one build on `//content` + selected `//components` without `//chrome`?

Technically yes (that is what CEF's Alloy style and `content_shell` do), and `//components/{extensions,autofill,password_manager,omnibox,history,bookmarks}` are designed to be embedder-agnostic. But `chrome/browser/` holds the *glue* for every feature (`ChromeContentBrowserClient`, profiles, prefs, extension system bootstrap, sync-less identity, printing, PDF, media router, policy, keystone/updater, sandbox entitlements, Mac app controller, crash handling). CEF's Alloy docs say exactly this: Alloy "provides less default browser functionality" than Chrome style, which "adds implementations for many advanced features (including datalist/autofill, extensions, gamepad, webhid, webmidi, etc.)" ([CEF architecture](https://chromiumembedded.github.io/cef/architecture)). Precedents: Opera 15 (2013) kept `//chrome` and replaced the UI layer; Vivaldi keeps `//chrome` and draws its UI in HTML; Arc/Dia keep `//chrome` with a Swift UI (closed source; see §7). Nobody ships a general-purpose browser on bare `//content`. **Recommendation: keep `//chrome`, replace the window.**

## 5. Swift integration options

### 5.1 Compiling `.swift` inside GN

- Chromium's Apple toolchain defines `tool("swift")` **only** `if (toolchain_args.current_os == "ios")`, with the comment: "Swift is only used on iOS, not macOS. We want to minimize the number of Xcode-based tools used by the macOS toolchain, so we intentionally disallow future uses of Swift on macOS. https://crbug.com/965663." ([build/toolchain/apple/toolchain.gni](https://github.com/chromium/chromium/blob/main/build/toolchain/apple/toolchain.gni))
- `build/config/apple/swift_source_set.gni` exists (template "for Swift source files"; module name derived from the label) and references `//build/config/ios:swift_cxx_interop` / `swift_cxx_interop_includes`. `build/config/ios/BUILD.gn` has `config("swift_cxx_interop") { swiftflags = ["-cxx-interoperability-mode=default", …] }` gated by `enable_swift_cxx_interop`, and a `swift_buildflags` header with `ENABLE_SWIFT_CXX_INTEROP` / `HAS_SWIFT_6_3_SUPPORT`. Chromium iOS has real Swift (`ios/chrome/test/swift_interop/*` with `polymorphism_xctest.swift` etc.) and has run Swift/C++ interop tests on its waterfall since 2022 ([Swift forums: "Chromium and Swift/C++ interop", Mike Pinkerton, Feb 28 2022](https://forums.swift.org/t/chromium-and-swift-c-interop/55642)).
- Therefore: **a fork can enable Swift for macOS with a small toolchain patch** (lift the `current_os == "ios"` condition and port the `swift_cxx_interop` config out of `//build/config/ios`). It is unsupported upstream and will need babysitting on toolchain rolls, but the machinery (swiftc wrapper `swiftc.py`, module maps, `-Xcc` flags) is all there.

### 5.2 Link a Swift framework built by Xcode/SwiftPM, bridge via ObjC++

- Chromium's sanctioned mixing model is Objective-C++: "If Objective-C++ works in the context needed, it is the preferred way to accomplish mixing"; keep ObjC out of `.h` (pimpl, `@class` forward decls, `base/apple/owned_objc.h`); ARC is on; "Never include `<objc/objc.h>` in headers" ([docs/mac/mixing_cpp_and_objc.md](https://github.com/chromium/chromium/blob/main/docs/mac/mixing_cpp_and_objc.md)). Nothing about Swift.
- Practical shape: your `BrowserWindow` subclass is a `.mm` file that owns an `NSWindowController` written in Swift (exposed via `@objc` / `@objcMembers`), and your Swift code calls back into C++ through a thin `@objc` protocol implemented in ObjC++. The Swift framework is built by Xcode/SwiftPM and copied into `Contents/Frameworks/` (GN `bundle_data` + a `copy` step), or compiled by GN after §5.1.
- Runtime considerations:
  - Chromium links its **own libc++** (`use_custom_libcxx = true` by default; "Bringing your own C++ standard library is deprecated and will not be supported in the future") with `_LIBCPP_ABI_NAMESPACE __Cr` and `_LIBCPP_ABI_VERSION 2` ([build/config/c++/c++.gni](https://github.com/chromium/chromium/blob/main/build/config/c++/c++.gni), [buildtools/third_party/libc++/__config_site](https://github.com/chromium/chromium/blob/main/buildtools/third_party/libc++/__config_site)). Any `std::` type crossing the boundary between Xcode-compiled code (system libc++, namespace `std::__1`) and Chromium code (`std::__Cr`) is a different type with a different mangled name — link errors at best, silent ABI corruption at worst. **Keep the ObjC bridge C/ObjC-only (NSString, NSArray, blocks, C structs); never pass `std::string`/`std::vector`/`base::` types across.**
  - Chromium replaces `malloc` with its allocator shim/PartitionAlloc (`use_allocator_shim`, `use_partition_alloc_as_malloc` in `base/allocator/partition_allocator/partition_alloc.gni`). Swift/ObjC runtime allocations will go through the shim; this is how all of Chromium's own ObjC already runs, so it is fine, but it means you cannot `free()` in one world what was allocated with a different allocator in another — again, keep ownership on one side.
  - Chromium builds with `-fno-exceptions` and no RTTI; Swift's C++ interop expects neither, but your bridge must not throw across frames.
  - Rust is also in the Chromium process (`enable_rust=true` in all the forks' flags); irrelevant to Swift but note the allocator interplay ("fix-rust-allocator-in-component-builds.patch" in Helium).

### 5.3 Swift C++ interop (Swift 5.9+) directly against Chromium headers

- Feasible in principle: Chromium iOS does it, with `-cxx-interoperability-mode=default` and bridging module maps. Pitfalls specific to Chromium:
  - You must compile Swift against Chromium's libc++ headers and defines (`-Xcc -nostdinc++ -Xcc -isystem buildtools/third_party/libc++/trunk/include`, `__config_site`), otherwise `std::` types are the wrong ABI (see above). The Swift compiler ships its own libc++ module map and has had repeated breakages when the module map/paths differ ([swiftlang/swift#76325](https://github.com/swiftlang/swift/issues/76325), [#74696](https://github.com/swiftlang/swift/issues/74696)).
  - `raw_ptr<T>`/`raw_ref<T>` (BackupRefPtr), `base::WeakPtr`, `base::OnceCallback`, `scoped_refptr` are templates Swift's importer handles poorly (non-trivial copy/move, custom operators); you will end up writing ObjC++ shims anyway.
  - Chromium's headers need ~50 `-D`/`-I` flags from GN; reproducing them for `swiftc` outside GN is brittle. Doing it *inside* GN (§5.1) is the cleaner path.
- **Recommendation:** ObjC++ bridge for all C++ ↔ Swift traffic; use C++ interop, if at all, only for simple value types and only after §5.1 lands.

## 7. Distribution (signing, notarization, updates)

- **Bundle layout and signing parts** (`chrome/installer/mac/signing/parts.py`): `<App>.app` → `Contents/Frameworks/<Product> Framework.framework/Versions/<ver>/` containing the dylib, `Helpers/<Product> Helper.app`, `Helper (Renderer).app` (entitlements `helper-renderer-entitlements.plist`), `Helper (GPU).app` (`helper-gpu-entitlements.plist`), `Helper (Alerts).app` (`…AlertNotificationService` bundle id), `Helper (Aperitif*).app` variants, `chrome_crashpad_handler`, `app_mode_loader`, `web_app_shortcut_copier`, plus an optional `UpdaterPrivilegedHelper`. ## 9. Effort estimate (judgment)

Assumptions: two strong engineers, one fluent in Chromium/C++ and one in AppKit/Swift; macOS-only; goal is a shippable browser (tabs, sidebar, omnibox, extensions from the Web Store, downloads, find, permissions, autofill, passwords, print, PDF, DevTools, auto-update, notarized).

### Route A — Chromium fork + native AppKit chrome (hybrid: native shell, Views for secondary UI)

| Phase | Work | Calendar (2 people) |
|---|---|---|
| 0. Infra | Checkout/tarball pipeline, GN args, `chromium_src`-style overlay dir, patch tooling, Depot/self-hosted CI with the 20-job resume pattern, codesign/notarize/DMG, Sparkle. | 3–5 weeks |
| 1. Window shell | `BrowserWindow` subclass in ObjC++ wrapping a Swift `NSWindowController`; host `WebContents` NSViews; tab switching via `TabStripModel`; command dispatch (`BrowserWindowCommandHandler`); fullscreen/`ExclusiveAccessContext`; status bubble; find bar; patch `browser_window_factory.cc`. Stub the remaining virtuals. | 6–10 weeks |
| 2. Omnibox | Native `OmniboxView` + popup over `OmniboxController`; security chip; `LocationBar` interface. | 4–8 weeks |
| 3. Secondary UI | Keep Views bubbles/dialogs anchored by rect; implement `ExtensionsContainer` natively (popovers hosting extension WebContents); infobar container; download UI (native or minimal); permission prompt factory (chip + bubble); autofill popup factory. | 8–14 weeks |
| 4. Polish & a11y | VoiceOver on the native chrome, keyboard equivalents, IME, drag-and-drop of tabs/URLs, Handoff, touch bar, menu bar, AppleScript. | 4–8 weeks |
| 5. First upstream rebases | Expect the first 2–3 milestone bumps to each cost days while the overlay settles. | ongoing |

**Total to a credible beta: ~7–11 months of two people**, then **~20–30% of one engineer permanently** for rebases at the 2-week cadence (or ~10–15% on Extended Stable + weekly security refreshes), plus CI spend (~$30–80 per release build on Depot, or one Mac mini). Risks that can double this: autofill/password UX parity, extension popup edge cases, accessibility, and Google refactoring `chrome/browser/ui/views/frame/` under you (it is actively being reorganised — `BrowserWidget`, `BrowserNativeWidget`, `browser_window/public/`).

### Route B — CEF + Swift/AppKit shell

| Phase | Work | Calendar |
|---|---|---|
| 0. Infra | SwiftPM/CefSwift bundling, signing, Sparkle. No Chromium build at all; CEF binaries track Chromium releases. | 1–2 weeks |
| 1. Shell | AppKit window, tabs = multiple `CefBrowser`s with `SetAsChild(parent NSView)`; omnibox is your own text field + CEF navigation; find via `CefBrowserHost::Find`. | 4–6 weeks |
| 2. Features | Downloads, permissions, JS dialogs, context menus, print, PDF, DevTools via CEF handler callbacks; autofill/password manager = **not provided in Alloy style** (you write them or do without); extensions: Chrome-style windows support "Tabs, extensions, chrome:// pages — full browser UI" but only as CEF's Views-based window, **not** inside your NSView ("Alloy style is always used if … parent_view is provided"). | 6–10 weeks |

**Total to a beta: ~3–4 months of two people**, near-zero rebase tax (upgrade CEF binaries per milestone; API is "production-quality stable"). The cap: Alloy-style embedding "provides less default browser functionality"; the Chrome-runtime goodies ("datalist/autofill, extensions, gamepad, webhid, webmidi, etc., along with standard Chrome UI toolbars and dialogs") come only with CEF's Chrome-style window and its Views UI. For a product whose differentiator *is* the native chrome and which needs Chrome extensions inside that chrome, CEF is a dead end you would eventually have to leave; for a product that can live with "web view in a nice shell" (no extensions, basic autofill), CEF is the right call.

### Which to choose

- If extensions-from-the-Web-Store, password manager, autofill, sync-like account features and Chrome-parity site compatibility are must-haves → **Route A**, with the hybrid scope, and accept that one person is a Chromium integrator for a year.
- If you are validating a UI concept → **Route B** first (3 months), knowing the migration to A later means rewriting the engine integration layer but keeping all AppKit/Swift UI code.
- Either way, do not try to go fully native on day one; the `ShowXxxBubble` long tail is where projects stall.

## 10. Open questions

1. **Exact M1 Max release-build time** with the flags you'd actually ship (`is_official_build`, ThinLTO, PGO): no primary report found; measure it in week 0 (expect 3–6 h). Kinard's M4 Max/M5 posts could not be fetched (Medium blocks scrapers).
2. **Is Helium's CI on Depot or GitHub-hosted runners?** The workflow's `runner` input defaults to `macos-latest` (3-core, 7 GB, 14 GB SSD — implausible for Chromium), while the README credits Depot; they likely dispatch with a Depot label. Not verified.
3. **Translate/Spellcheck/Suggest ToS for derived products** — the API-keys page is silent on `translate.googleapis.com`; nothing found that forbids it, nothing that guarantees it.
4. **Widevine license path for a small company** — Greenblatt says free via component updater; Helium says "Google restricts Widevine licensing to its partners". Both can be true (free but gated). Apply early; the answer determines whether you can promise Netflix/Spotify.
5. **Chrome Web Store brand label and future gating** — the store relies on the browser's reported brand/UA; whether Google will tighten store access for non-Chrome brands is unknown.
6. **How much of `BrowserView` do callers reach through `AsBrowserView()`?** Count the call sites that would crash on `nullptr` before deciding the stub strategy (a `grep -r "AsBrowserView()" chrome/` on the pinned milestone).
7. **Swift in GN on macOS:** the crbug.com/965663 rationale ("minimize the number of Xcode-based tools used by the macOS toolchain") suggests a hermetic-toolchain concern; confirm whether Chromium's hermetic Xcode (`mac_sdk.gni`) ships `swiftc` or you must point GN at a full Xcode.
8. **Accessibility bridging** for a native tab strip/omnibox alongside Chromium's content AX tree — no reference implementation exists post-M70.
9. **Extended Stable availability to third parties** — Google publishes extended-stable branches in the public tree (every fourth milestone, 8-week cadence), but confirm the security-refresh tags land on those branches in time for a weekly backport.
